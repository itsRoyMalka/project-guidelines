# Outbox and consumer receipts

Owners: [EVT-02/03/08/09](../04-events-and-workflows.md), [BE-05/07](../01-service-design.md). Scope: reliable messages coupled to database state. Use the [transaction contract](transactions.md).

## The complete flow

```text
Producer transaction: business writes + outbox intent → commit
Relay: read committed intent → send through adapter → record delivery
Consumer transaction: receipt + business writes + new intent → commit
Transport: acknowledge committed progress
```

The outbox prevents losing required intent after a successful DB write. It does not prevent duplicate delivery. A per-consumer receipt prevents repeating the committed local effect. Neither guarantees exactly-once external effects.

| Need | Mechanism |
| --- | --- |
| DB change requires an event or workflow start | Same-DB transactional outbox |
| Consumer changes DB state | Receipt in the same transaction as the effect |
| Webhook must acknowledge before business processing | Durable inbox admission, then worker receipt/effect transaction |
| Telemetry may be dropped by declared policy | Bounded telemetry pipeline; no business outbox required |
| Simple in-process operation in one transaction | Direct public handler call; no broker required |

## Ownership and minimal records

```text
src/shared/transactions/                 # context and factory semantics
src/shared/messaging/                   # outbox, receipts, relay, dispatcher
src/integrations/events/                # broker ports and adapters
src/app/events/subscriptions.ts         # named feature registrations
src/features/orders/cancel-order/handler.ts
src/features/payments/request-refund/{consumer,handler}.ts
db/                                    # schema composition and migration history
```

Shared messaging owns its schema definitions under `shared/messaging/db/`; app `db/` composes them alongside feature schemas. These are infrastructure-owned operational records, not tables any feature edits directly.

| Record | Minimum responsibilities |
| --- | --- |
| Outbox message | Stable ID/source/type/contract version; immutable payload/time; correlation; optional aggregate sequence and trusted scope |
| Delivery | Unique message/destination; state, attempts, next attempt, lease token/expiry, safe failure code and delivery time |
| Consumer receipt | Unique consumer/source/event ID; completion time; identity/payload consistency evidence where required |

One destination can combine message/delivery storage. Multiple destinations keep independent progress; record the destination set with intent, or version its routing policy so deployments cannot silently drop pending deliveries. A mutable status alone is not an atomic claim.

Tenant data is present only for a multi-tenant product and comes from verified scope. Event IDs must be unique within their producer source; that identity is preserved across retries and routes. Validate sender and identity before deduplication; conflicting content under an existing identity is rejected/quarantined, not processed as a new event.

## Producer: only committed intent can escape

The transactional handler writes business state and calls `deps.outbox.add(db, event)`. Failure of either write rolls back both. The event ID is assigned before any delivery and never regenerated by the relay. Required audit and idempotency results join the same transaction when applicable.

Only the relay receives the broker publish capability. Keep it out of feature dependencies; enforce feature import boundaries. A best-effort after-commit callback may wake the relay, but cannot be the sole record of pending work.

## Relay: expect resend

1. Claim a bounded due batch in a short DB transaction; commit the lease before network I/O.
2. Publish outside the DB transaction with the original event identity.
3. Record each confirmed destination separately, conditional on the current lease token. A stale worker cannot overwrite the current claim.
4. Retry ambiguous or failed sends under bounded policy; alert and retain exhausted work for owned recovery.

If the relay crashes after sending, it may send again. Check per-item results for batch APIs. Broker acceptance proves acceptance at that boundary, not completion of downstream business effects. Never purge pending work because its normal retention age elapsed.

Parallel claims do not imply ordering. When aggregate order matters, define sequence, route/partition key and dispatch/retry policy for that aggregate. Consumers explicitly handle stale events and gaps; timestamps alone are insufficient.

## Consumer: one receipt per logical subscriber

```ts
// features/payments/request-refund/consumer.ts — project-owned factory
export const requestRefund = defineConsumer({
  name: PaymentConsumer.RequestCancellationRefund,
  event: OrderCancelled,
  handle: requestRefundHandler,
});
```

The dispatcher follows this protocol, not feature-authored receipt code:

```text
verify producer + contract + trusted execution scope
begin transaction
  atomically INSERT receipt key if absent
  if already committed: skip this consumer's effect
  otherwise: invoke handler using the same transaction
             commit business changes + any new outbox intent + receipt
commit
acknowledge
```

Use database-supported conflict handling such as `INSERT ... ON CONFLICT DO NOTHING`; do not catch a uniqueness error and continue an aborted PostgreSQL transaction. Concurrent duplicates wait/retry within bounds; they are not acknowledged based on an uncommitted reservation. A handler failure rolls back the receipt too.

Two consumers of the same event have different names and both run. Renaming a consumer changes durable identity and requires a replay/migration decision. Consumer receipts remain available for the supported redelivery/replay window; older replay needs an explicit rebuild/reconciliation plan.

Adapters map acknowledgement to the actual transport. Queue messages are acknowledged after durable progress; Kafka offsets advance only over contiguous completed or durably admitted records within a partition. A later successful record cannot skip earlier unfinished work.

An inbox admission is different from a completed receipt: persist pending work before acknowledging ingress; its worker later commits receipt plus effect. An accepted webhook is not a completed payment. Keep pending admission recoverable, and durably quarantine unsupported/poison input before treating it as handled.

Central audit delivery uses the same durable envelope/receipt mechanics; [audit policy](audit.md) owns its fields, outcome semantics and retention. A business event is not automatically a complete audit record.

## External effects and jobs

A refund consumer commits a pending refund operation and durable job intent, not a claim that the payment provider refunded it. A worker calls the provider outside the DB transaction using a stable operation key; it reconciles unknown outcomes under the [external-outcome protocol](idempotency.md). Completion is a later state change/event.

Use the same durable-intent boundary when a DB write requires starting Temporal or another job provider. The relay starts with a stable execution identity and reconciles duplicate/unknown starts. The engine does not share the application's DB transaction. Do not automatically add another outbox inside every Activity; apply it only when that Activity's DB state and outgoing work must agree.

## Failure checks

| Inject | Required observation |
| --- | --- |
| Handler/outbox failure before commit | No business change and no publishable intent |
| Broker unavailable after DB commit | Business state and pending intent survive; relay eventually retries |
| Relay crash after send, before record | Delivery may repeat; each consumer effect commits once |
| Consumer failure after receipt insert | Receipt and writes roll back; retry can complete |
| Consumer commit then lost acknowledgement | Redelivery skips committed local effect |
| Two consumers receive the same event | Both effects occur, each once |
| Out-of-order event or expired receipt history | Selected gap/stale/replay policy applies explicitly |

Use real DB/outbox/dispatcher code with an app-scoped recording transport for these integration checks. Adapter-specific lease, offset and delivery guarantees need separate provider proof. Monitor oldest pending intent, attempts, expired leases, consumer lag and dead letters with bounded labels.

**Alternative:** verified CDC may supply the same durable publication guarantee. A naturally idempotent conditional write can replace a receipt only when its invariant covers all effects and replay cases; document and test that substitution.
